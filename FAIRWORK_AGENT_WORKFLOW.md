# Fairwork — Code-Generation Workflow & Agent Rules

**Status:** Team working agreement  
**Project:** Fairwork — milestone-based freelance agreements, evidence, disputes, and test escrow  
**Primary coding tool:** Cursor  
**Secondary coding tool:** Antigravity  
**UI design tool:** Stitch  
**Team size:** Four developers

---

## 1. Purpose

These rules exist to prevent duplicated work, uncontrolled AI-generated code, conflicting edits, oversized implementations, and late integration failures.

The team uses **one implementation owner** to coordinate code generation and integration. Other developers may generate code only for explicitly assigned, isolated tasks in separate branches or worktrees. All implementation must follow approved requirements, designs, architecture, and interfaces.

The objective is not to generate the most code. It is to deliver the smallest reliable implementation that satisfies the agreed requirements.

## 2. Non-Negotiable Principles

1. **Humans decide what to build.** Agents implement approved tasks; they do not expand the product scope independently.
2. **Cursor is the primary coding tool.** Antigravity is secondary and may review, plan, diagnose, or implement isolated assigned work.
3. **One active writer per file.** Two agents must never edit the same file concurrently.
4. **No uncoordinated shared-repository edits.** Secondary code generation requires an explicitly assigned task and an isolated branch/worktree.
5. **Design before implementation.** Stitch designs the main pages; the team then proposes and approves reusable components before page implementation begins.
6. **Integrate after every phase.** Do not allow parallel branches to accumulate until the end.
7. **Inspect before editing.** Agents must inspect relevant existing files and follow established patterns before creating or modifying code.
8. **Prefer reuse and compact code.** Do not duplicate components, services, utilities, validation, or configuration.
9. **No speculative architecture.** Do not introduce microservices, extra frameworks, unnecessary dependencies, or abstractions without approval.
10. **Humans control Git state changes.** Agents must not perform Git add, commit, push, merge, rebase, branch switching, checkout, reset, cherry-pick, or other Git state-changing operations.

## 3. Team Roles

Assign actual team members to these roles before implementation starts.

### Developer 1 — Implementation Owner

- Owns the main integration branch and coordinates implementation.
- Uses Cursor as the primary code-generation environment.
- Maintains the approved task queue and file ownership list.
- Reviews all agent-generated diffs before integration.
- Ensures naming, architecture, API contracts, and shared components remain consistent.
- Coordinates integration after each phase.
- Does not automatically accept code generated by Cursor or Antigravity; code must pass review and tests.

### Developer 2 — UI/UX and Stitch Owner

- Designs the main Fairwork pages in Stitch.
- Documents user flows, page states, responsive behavior, and interaction details.
- Proposes reusable components after the main pages are designed.
- Maintains the agreed design tokens and component inventory.
- Reviews implemented UI against Stitch designs.
- Does not independently regenerate the whole frontend in a coding agent.

### Developer 3 — Backend and Blockchain Owner

- Defines API contracts, database schema, business rules, and smart-contract boundaries.
- Documents request/response formats, status transitions, validation rules, and error responses.
- Reviews backend and contract logic for correctness and security.
- Coordinates with the implementation owner before any schema or API change.
- Does not silently change shared interfaces after frontend implementation has started.

### Developer 4 — QA, Integration Support, and Documentation Owner

- Converts approved requirements into acceptance criteria and test cases.
- Tests each phase and records reproducible defects.
- Reviews authorization, invalid state transitions, duplicate actions, and failure handling.
- Maintains integration notes, known issues, and demo readiness.
- May implement a narrowly assigned fix only in an isolated branch/worktree with explicit file ownership.

**All four developers participate in planning and reviews.** Role ownership clarifies accountability; it does not prevent other developers from contributing ideas or reporting issues.

## 4. Tool Responsibilities

### Cursor — Primary Implementation Tool

Use Cursor for the main implementation workflow:

- Read repository rules and relevant files before making changes.
- Propose a plan and list files to be changed.
- Implement one approved task at a time.
- Reuse existing components and patterns.
- Run relevant tests, type checks, linting, and builds.
- Inspect the final diff and summarize the result.
- Stop and ask for clarification when requirements or interfaces conflict.

### Antigravity — Secondary Tool

Use Antigravity for one of these clearly assigned purposes:

- Review a proposed implementation or diff without editing files.
- Diagnose a reproducible bug and propose a minimal fix.
- Generate a plan or test cases.
- Implement a small isolated task in a dedicated branch/worktree when authorized.

Before Antigravity writes code, the implementation owner must record the task, owner, permitted files, branch/worktree, acceptance criteria, and integration plan. Antigravity must not modify files currently being edited by Cursor or another developer.

### Stitch — UI Design Source

Use Stitch to design the main pages and identify the common visual language. Stitch output is a design reference, not permission to generate an entire application automatically.

The UI owner must document:

- Page purpose and user roles.
- Navigation and key user flows.
- Reusable components and design tokens.
- Form fields, validation, loading, empty, success, and error states.
- Responsive behavior.
- Interactions that require backend APIs.
- Any visual or interaction details not represented in the design.

## 5. Required Workflow

### Phase 0 — Understand and Plan

Before code generation, all developers must:

1. Read the complete problem statement and approved Fairwork feature list.
2. Discuss the user problem, MVP scope, and critical workflows.
3. Agree on architecture, data model, API contracts, and status transitions.
4. Identify external integrations and label any mocked functionality.
5. Define acceptance criteria and the demo path.
6. Record decisions in repository documentation.

Do not start broad code generation while requirements remain unresolved.

### Phase 1 — Design in Stitch

1. Design the main pages and primary user flows.
2. Review the pages as a coherent product, not as isolated screens.
3. Identify repeated UI patterns.
4. Propose reusable components and shared design tokens.
5. Approve the component inventory before implementing multiple pages.
6. Record design references and any behavior that needs clarification.

Suggested initial pages:

- Landing page
- Authentication
- Dashboard
- Project list and project details
- Agreement and milestones
- Submission and progress
- Disputes
- Payments and activity

### Phase 2 — Freeze Shared Interfaces

Before parallel implementation, agree on:

- Repository and folder structure.
- Frontend routes and shared component interfaces.
- API paths and request/response schemas.
- Database tables, relationships, and migration conventions.
- Shared status enums and valid transitions.
- Error response format.
- Environment variable names.
- Test and build commands.

Any change to a shared interface requires a written proposal, impact assessment, and approval from the affected owners.

### Phase 3 — Build the Foundation

Implement and verify:

- Application entry points and configuration.
- Shared layout and approved design tokens.
- Database connection and migrations.
- Authentication and authorization foundations.
- Error handling and validation conventions.
- Test setup and environment examples.

Do not implement all feature pages before the foundation is tested.

### Phase 4 — Implement Vertical Slices

Build one complete, testable workflow at a time. A vertical slice includes the UI, API integration, backend logic, persistence, validation, and tests required for that workflow.

Recommended order:

1. Authentication and role-aware layout.
2. Project creation and invitations.
3. Versioned agreements and milestone creation.
4. Submission, revision, and review.
5. Test escrow funding and payment tracking.
6. Disputes and evidence.
7. AI assessment and deadline notifications.
8. Optional external integrations.

For each slice:

1. State the task and acceptance criteria.
2. Identify allowed files and dependencies.
3. Inspect existing code.
4. Write a short implementation plan.
5. Make the smallest useful change.
6. Run relevant tests and builds.
7. Review the diff for scope and duplication.
8. Demonstrate the behavior.
9. Record remaining issues.
10. Integrate before beginning dependent work.

### Phase 5 — Integration Checkpoint

At the end of every phase:

- Stop new feature work temporarily.
- Inspect all changed files and diffs.
- Resolve interface conflicts.
- Run unit and integration tests.
- Run linting, type checks, and builds where configured.
- Verify the feature against Stitch and acceptance criteria.
- Update documentation and known issues.
- Have the human Git owner perform approved Git operations.
- Begin the next phase only after the checkpoint passes or remaining blockers are explicitly accepted.

## 6. Parallel Work and File Ownership

Parallel work is allowed only when tasks are genuinely independent.

Every parallel task must have a written assignment containing:

- Task ID and objective.
- Assigned developer and tool.
- Branch/worktree name created by the human Git owner.
- Explicit list of files or directories allowed to change.
- Files that must not be changed.
- Dependencies and shared interfaces.
- Acceptance criteria and test commands.
- Expected output and integration notes.

### Rules

- A file has exactly one active writer at a time.
- If two tasks need the same file, sequence them or split the interface deliberately before coding.
- Do not create a second version of an existing component or service just to avoid coordination.
- Do not change package manifests, lockfiles, shared configuration, database migrations, or API contracts without explicit permission.
- Do not copy an entire module into a new directory to make a local change easier.
- Secondary branches/worktrees must be created and managed by the human Git owner.
- After the task passes review, the human Git owner performs integration.
- If conflicts arise, stop and report them; do not resolve them through unapproved Git operations.

## 7. Agent Communication Through `devname.md`

Each developer maintains a communication file named after their agreed short identifier, for example:

- `anto.md`
- `dev2.md`
- `dev3.md`
- `dev4.md`

Use the actual team members' agreed identifiers. Keep these files in the agreed coordination directory, such as `coordination/`, rather than scattering them through source folders.

Agents must read relevant coordination files before starting a task and update their own file when they need input, finish work, discover a conflict, or are blocked.

### Required message format

```md
## [TASK-ID] Short title
- Status: REQUEST / IN_PROGRESS / BLOCKED / READY_FOR_REVIEW / DONE
- From: <developer or agent>
- To: <specific developer or role>
- Request: <specific question, decision, or action needed>
- Context: <relevant files, API, schema, or design reference>
- Impact: <what work is blocked or affected>
- Needed by: <phase/checkpoint>
- Response: <recipient fills in response or links their answer>
```

### Communication rules

- Address a specific person or role; do not write vague requests to "everyone."
- Include file paths, task IDs, and exact questions.
- Never assume another developer saw a message; acknowledge important interface decisions.
- Record decisions that affect other tasks in the relevant shared specification.
- Do not use `devname.md` files as a substitute for API documentation or architecture records.
- Remove or archive resolved requests according to the team's chosen convention; do not silently erase unresolved decisions.

## 8. Code Generation Limits

Agents must follow these rules for every task:

1. **No giant prompts.** One prompt should implement one bounded task, not the entire application.
2. **No giant rewrites.** Do not regenerate a whole directory or application when a small change is sufficient.
3. **No unrequested features.** Ask before expanding scope.
4. **No duplicate infrastructure.** Reuse existing routing, components, services, validation, logging, and database access.
5. **No placeholder sprawl.** Do not create many empty files, speculative modules, mock screens, or TODO-only implementations.
6. **No unexplained dependencies.** Explain the need and obtain approval before adding packages.
7. **No unapproved architectural changes.** Follow the agreed stack and module boundaries.
8. **No hidden behavior.** Explain significant state transitions, side effects, and external calls.
9. **No fake success.** Never show a payment, AI assessment, integration, or transaction as real when it is mocked or unverified.
10. **No secrets in code.** Use environment variables and maintain `.env.example` without real credentials.
11. **No unnecessary comments or abstractions.** Write comments for non-obvious decisions; prefer clear, direct code.
12. **No deletion of unrelated work.** Preserve other developers' changes.
13. **No blind acceptance.** Generated code must be inspected and tested by a human.
14. **No autonomous Git state changes.** Agents must not add, commit, push, merge, rebase, switch branches, checkout, reset, cherry-pick, or otherwise alter Git state.

### Scope guard

Before editing, the agent must state:

- What it will implement.
- Which files it expects to modify.
- Which files it will not touch.
- Which tests it will run.

If the task appears to require broader changes, stop and ask the implementation owner for approval.

## 9. Fairwork-Specific Correctness Rules

- A freelancer may submit a milestone but cannot approve their own submission.
- Only authorized project participants may access project details and private evidence.
- Agreement changes create a new version; the previous accepted version remains available.
- A proposed agreement change is not active until the required parties accept it.
- Milestone status transitions must follow the agreed state machine.
- AI assessments are advisory and must not make final dispute decisions or authorize transfers.
- A file hash helps detect changes; it does not prove quality, authorship, or correctness.
- PostgreSQL status alone is not proof that an on-chain transaction succeeded.
- Verify transaction receipts and relevant contract events before showing settlement as confirmed.
- Never claim escrow funds are locked unless the deployed/test contract actually enforces it.
- Use local-chain or testnet funds for the hackathon demo; label simulated behavior clearly.
- Do not claim control over external marketplace contracts or payments without authorized integration.
- Keep private evidence out of public logs and unauthorized model requests.

## 10. Testing and Review Gate

A task is not complete merely because code was generated.

Before marking a task ready for review, the implementer must provide:

- Summary of the behavior implemented.
- List of changed files.
- Tests added or updated.
- Exact test/build commands run and their results.
- Known limitations or untested cases.
- Screenshots or a short demonstration for UI work where practical.
- Confirmation that the diff contains no unrelated changes.

Reviewers should check:

- Does it meet the acceptance criteria?
- Does it reuse existing components and conventions?
- Is there duplicated or unnecessary code?
- Are validation, permissions, loading, error, and empty states handled?
- Are shared interfaces unchanged or explicitly approved?
- Do tests fail for the right reasons and pass after the fix?
- Does the implementation match the Stitch design?
- Are secrets and private data protected?
- Are mocked and real behaviors clearly distinguished?

If tests fail, report the exact command and failure. Do not claim tests passed if they were not run.

## 11. Human Git Ownership

Agents must not execute Git state-changing commands, including:

- `git add`
- `git commit`
- `git push`
- `git merge`
- `git rebase`
- `git checkout`
- `git switch`
- `git reset`
- `git cherry-pick`
- `git stash`
- Commands that alter branches, the index, or repository state

Agents may inspect repository files and, if permitted, run read-only inspection commands such as `git status`, `git diff`, and `git log`. They must not modify Git state.

The human Git owner is responsible for creating branches/worktrees, staging, committing, pushing, merging, and resolving integration conflicts. Before integration, inspect the changed-file list and diff, run tests, and confirm that no unrelated changes are included.

---

## 12. Definition of Done

A feature or phase is done only when:

- [ ] The approved acceptance criteria are satisfied.
- [ ] The implementation follows the agreed architecture and design.
- [ ] Shared interfaces and status transitions remain consistent.
- [ ] Relevant tests and build checks pass.
- [ ] The diff has been reviewed for scope, duplication, and unintended changes.
- [ ] UI behavior matches the approved Stitch reference.
- [ ] Security and authorization requirements are checked.
- [ ] Mocked behavior is clearly labelled.
- [ ] Documentation and coordination notes are updated.
- [ ] The human Git owner has reviewed and integrated the change.

## 13. First Tasks for the Team

Before generating the first feature:

1. Confirm the four developer role assignments.
2. Review the Fairwork project overview and frontend/backend architecture documents.
3. Design the main pages in Stitch.
4. Approve the shared design tokens and reusable component inventory.
5. Approve the backend API contracts, database schema, and shared state enums.
6. Create `AGENTS.md` with these rules and individual `devname.md` coordination files.
7. Select the first vertical slice and define its acceptance tests.
8. Have the human Git owner create the required branch/worktree.
9. Use Cursor to implement the first bounded task.
10. Run the first integration checkpoint before expanding scope.

**Final rule: one product specification, one shared architecture, one active writer per file, small reviewed changes, and a tested integration checkpoint after every phase.**
